# Daily publication scheduling and monitoring

## What is known

`30 22 * * *` is 22:30 UTC, or 06:30 the next day in Asia/Shanghai. A successful manual `workflow_dispatch` proves neither that `schedule` is enabled nor that a scheduled event was delivered. GitHub may delay or drop schedules; scheduled workflows in forks are disabled by default, and scheduled workflows in public repositories can be disabled after inactivity. The scheduler's actor and account status can also affect execution. Check Actions settings, the workflow's enabled state on the **default branch**, the schedule actor and the scheduled-run history; we have not verified this repository's actual enabled state or Cloudflare deployment. See [GitHub's schedule troubleshooting](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows) and [enabling workflows](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows).

## Deployment and safe cutover (owner-operated)

Do not execute these steps merely to test this PR; merging and deployment require separate review. Use the owner's existing Worker and Secrets; never put credentials into source, logs, artifacts, or a command shown publicly.

1. Ensure the reviewed workflow is on the default branch. Check GitHub Actions is enabled, and note the existing GitHub scheduled trigger for rollback. Confirm the worker identity can send repository dispatch and read workflow runs and jobs: a fine-grained token needs repository **Contents: read/write** for dispatch and **Actions: read** for monitoring, limited to this repository. Store it as Worker Secret `GITHUB_PAT`; configure non-secret Worker variables `GITHUB_OWNER` and `GITHUB_REPO`. Keep the existing `TRIGGER_SHARED_SECRET` as a separate strong Worker Secret. Requests to the existing GET endpoint require the `X-Worker-Trigger-Secret` header; an unconfigured or wrong secret is rejected. Treat authenticated calls as real publication requests, not probes.
2. Configure `ALERT_WEBHOOK_URL` as a Worker Secret pointing to a private HTTPS endpoint that accepts a JSON POST with `event`, `day`, and `status`. Verify the receiver and notification route independently. A missing or failed webhook produces a safe Worker log, **not** a delivered notification. Do not use a URL with credentials embedded in it. No secrets, private URLs, article content or provider responses are included in alerts.
3. Deploy this Worker and both cron entries with `SCHEDULER_MODE=dry_run` or unset. Observe a scheduled 06:30 `dispatch`/`dry_run` log and the 07:00 monitor and alert path; no production dispatch occurs in dry run. Verify the Worker can read Actions state and the alert receiver receives a suitable test independently, without triggering the publication endpoint. The monitor itself is independent of the Daily Gather workflow, but depends on Cloudflare and GitHub availability.
4. To verify the **real dispatch** path, have the owner explicitly set `SCHEDULER_MODE=active` while retaining the native GitHub schedule. Observe an actual scheduled event and its run through verified WebDAV delivery. This is a production action and must be explicitly authorized by the owner; never use the authenticated HTTP endpoint as a connectivity test. During overlap the daily gate attempts to suppress a second successful publication. Do not disable the native trigger until the new trigger has actually been observed working.
5. Once verified, the owner removes or disables the GitHub `schedule` trigger on the default branch, retaining `workflow_dispatch` and `repository_dispatch`. Keep exactly one **publication** scheduler: the Worker 06:30 cron. The separate 07:00 cron only monitors, and never republishes. Cloudflare deployment is not implied by a successful code test.
6. Production acceptance requires at least three successive scheduled publication cycles with real automatic dispatch, EPUB generation, verified WebDAV delivery and observable failure notifications. Record dates, run IDs and outcomes privately. Offline tests and a successful dispatch HTTP response do not establish this acceptance.

## Monitoring and interpretation

The 07:00 Worker queries today's Shanghai-time Daily Gather runs and their `gather` job step conclusions. It logs and sends an alert for `not_started`, `running`, `epub_missing`, `webdav_failed`, `webdav_unknown`, `ai_degraded`, `status_unavailable`, or `monitor_error`. `running` can simply mean a slow or delayed run; investigate rather than blindly republish. A health JSON artifact contains only status flags. EPUB generation means a nonempty EPUB file was present; WebDAV success comes from the existing uploader's verification. A disabled AI is reported separately and does not alert. An error in the monitor or alert transport is logged by category, without GitHub response bodies or credentials; a broken Worker cannot alert on its own absence, so use external platform uptime/alerting as appropriate.

The monitor examines Daily Gather, not the separate encrypted retry workflow: a successful subsequent retry must be checked manually and may not clear an already sent alert. A failed job before it can emit health markers yields `status_unavailable`. Test-only runs are excluded when their early marker executes. In a pathological backlog the GitHub API's first 100 results might not include the relevant run; investigate before acting. The marker step names are an interface shared with the Worker and must be changed together.

## Repeat publication and recovery

All production events and the existing Fresh Start / retry workflows share the existing Actions concurrency group. The new per-Shanghai-day cache marker is written only after EPUB existence and WebDAV success are verified, independently of publication dedup. A duplicate is skipped after that marker is restored; manual `test_mode` ignores and does not create it. To intentionally publish again after verified delivery, explicitly select `force_publish` in a manual run. This may produce a different edition; use it deliberately. For failed delivery, use **Retry WebDAV Delivery** and the existing encrypted backup to retry the same EPUB without fetching news again. A successful retry currently does not create the daily marker; inspect the retry result before triggering any further run. No automatic retry or history reset is introduced.

This guard is best effort, not an exactly-once lock: cache outages, eviction, branch scope, failure between delivery and marker save, late execution across Shanghai midnight, and explicit force can still permit duplicates. GitHub concurrency serializes runs but may replace an existing pending run; it is not a durable queue. If WebDAV is disabled or status is unavailable, no verified marker is saved. Never clear dedup history as a scheduling fix. Existing publication dedup, Fresh Start and test isolation retain their own semantics.

AI mode precedence is explicit manual `off`/`shadow`, then configured `AI_EDITOR_MODE`, then `shadow` for scheduled and repository dispatch events, otherwise `off` for manual runs. Set `AI_EDITOR_MODE=off` explicitly when no automatic AI call is desired. Existing budgets and Shadow failure isolation remain; no AI call is used by the monitor.

## Rollback

Have the owner first restore and verify the native GitHub 06:30 schedule on the default branch, then set Worker `SCHEDULER_MODE=dry_run` or disable only its publication cron. Monitor and investigate overlap using the daily marker; do not disable both before confirming a scheduler works. The 07:00 monitor may remain independently enabled. If rolling back the workflow itself, account for the fact that older code will not emit the monitor markers. Never expose or rotate secrets merely to roll back.
