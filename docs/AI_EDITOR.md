# Topic-first Shadow Editor

The Shadow Editor runs after ordinary EPUB generation, deduplication and delivery. It is disabled by default (`AI_EDITOR_MODE=off`) and never changes official selection, article order, EPUB, deduplication, delivery or memory. `test_mode` does not make paid calls unless the operator explicitly enables `run_ai_shadow`.

Shadow uses three stateless DeepSeek Responses API stages. Grouping sees all candidates within `AI_MAX_CANDIDATES` (default 200); unmatched candidates become singleton topics. One global audit then checks only multi-article groups and may split erroneous merges. It cannot merge groups: local validation requires every split to be a complete, disjoint partition of its original group, and generates stable IDs locally. Selection sees the audited topics and chooses up to 16 important independent stories and one representative for each. If there are no multi-article groups, the audit needs no call. A story is a concrete news thread, not a broad subject such as politics. The model is instructed to check its shortlist for duplicate stories. Local validation rejects invented or repeated candidate IDs, overlapping groups, invalid group IDs and more than one selection per group. An audit failure degrades Shadow without recommendations; there is no fallback to the former article-scoring algorithm.

Input contains short-lived IDs, titles, sources, language, dates and bounded RSS excerpts, never real candidate hashes, URLs, cookies or official selection status. A compact editorial profile can be supplied to selection; no raw feedback or memory is published. Candidates and excerpts are untrusted data; tools and thinking are disabled. Only local candidate titles, sources, IDs and group membership are written to the report. Each grouped topic gets one slot; `topic_groups` links the representative to the other candidates. The model does not see full articles and cannot determine their actual completeness or reliability from titles and snippets alone.

The same existing `AI_MAX_INPUT_TOKENS`, `AI_MAX_OUTPUT_TOKENS`, `AI_MAX_TOTAL_TOKENS`, `AI_MAX_CALLS_PER_RUN` and `AI_TOTAL_TIMEOUT_SECONDS` apply to both calls and retries. Input and maximum output are conservatively reserved before each request and known actual usage is refunded. Excerpts are uniformly shortened as needed to fit, without dropping candidates inside the configured cap. Candidate-cap truncation is explicitly reported. If either phase fails validation, times out or cannot fit the budget, the Shadow report is degraded and contains no purported final recommendations; the daily publication is unaffected. External provider token accounting is not a billing guarantee.

The report includes `topic_audit_status`, `audited_group_count`, `split_group_count` and `topic_count_after_audit`; `topic_count` counts groups before audit, while multi-article counts and `topic_groups` describe the audited result. `audit_splits` records locally reconstructed original group IDs and validated partitions, with candidate IDs and titles; it contains no raw model output. `excerpt_retention` records each stage's received nonempty excerpt count and, for each actual request attempt, the sent nonempty count, mean retained characters per candidate and total-character retention rate. Skipped or blocked stages have no attempts. It also includes selected topic/article counts, usage, memory status and traditional-selection comparison. Offline mock tests validate prompt content, response structure and local constraints; predetermined mock splits do not establish the model’s semantic ability. The model can still wrongly merge independent stories or split a single story into multiple groups: group uniqueness is not proof of real-world semantic uniqueness. Review the Shadow shortlist before considering any future official AI selection.

For manual testing only, configure the independent secrets described in [AI_MEMORY.md](AI_MEMORY.md), then run Daily Gather on the desired branch with `test_mode=true`, `upload_plaintext_epub=false`, `ai_editor_mode_override=shadow`, `run_ai_shadow=true`, `retry_failed=false`. This may incur API charges. CI uses mocks; do not place keys or private feedback in public workflow inputs.

Legacy article-batch and composition sizing variables (`AI_MAX_BATCH_CANDIDATES`, `AI_COMPOSE_MAX_CANDIDATES`, `AI_MAX_ARTICLES_PER_EVENT`) no longer control topic-first selection. Existing repository variables are not changed by this update.

## Budget allocation and diagnostics

Grouping protects a bounded share of input budget for later stages instead of reserving hypothetical worst-case audit and selection requests. Before reserving later requests or retries, it prioritizes up to 160 characters of each current excerpt when that fits. Audit calculates selection headroom from the actual groups, and selection is built from audited groups. If a retry is needed, excerpts can be shortened again; all candidates within the cap remain in the request. These reservations cannot guarantee subsequent requests will fit, so insufficient budget safely stops Shadow. Known usage is charged and unused reservations refunded; missing usage retains the full reservation. The report records `failed_stage`, `last_attempt_error_category`, `last_response_status`, `last_error_response_status`, `retry_attempted`, `retry_blocked_reason`, `budget_limit_hit` (resource and whether actual usage or reservation blocked progress), and `stage_api_calls`. These fields are fixed categories and never contain provider response bodies or private prompts. `last_attempt_error_category` retains the most recent failure even when a later retry succeeds.

For example, the operator may choose `AI_MAX_INPUT_TOKENS=120000`, `AI_MAX_OUTPUT_TOKENS=40000`, `AI_MAX_TOTAL_TOKENS=160000`, `AI_MAX_CALLS_PER_RUN=10`, and `AI_TOTAL_TIMEOUT_SECONDS=240`; this change does not set repository variables. Normal operation uses three calls when audit has groups to review, otherwise two. More budget cannot guarantee provider compliance or semantic grouping quality.

## Coverage and future capacity

`candidate_count` is the number collected, `candidate_cap` is the configured maximum considered, and `skipped_candidate_cap` records the rest. The current process is global **only within that capped pool**, not all collected news. CandidateCollector currently interleaves sources in sorted source-label order, with entries sorted by candidate hash rather than recency or importance. More than 200 source labels can therefore exclude later labels, and merged labels can affect representation. This is a deterministic sampling bias, not an editorial importance ranking.

For larger pools, a future design could conservatively filter invalid content, exact duplicates and high-confidence near duplicates locally; group stories in batches; merge topics globally across batches; select by topic importance; and retain one representative per story. It must check for repeated news threads across batches and remain bounded by run-wide token, call and time budgets. It should not use embeddings, a vector database, new paid services, mechanical source/region/field quotas, or article frequency alone as an importance score. This layered pipeline is a proposal, not implemented here; the current 200-candidate mode should be stabilized before choosing scale thresholds.
